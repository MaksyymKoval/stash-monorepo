# План MVP MakeupStash

Актуально на 11.11.2026

## Підсумок і принципи

MVP перевіряє три речі в такому порядку: чи легко зібрати косметичку (фото столу, сканер штрихкодів), чи швидко публікується образ із продуктами, і чи корисний «Повтори цей образ». Кожна має свій етап і свої цифри; спільнота й підготовка до сторів ідуть після них.

Принципи фундаменту:

- **Один репозиторій, два застосунки.** `apps/api`, `apps/mobile` і один спільний пакет зі схемами.
- **Кожна залежність і кожен шар мають причину.** Без репозиторіїв-обгорток, CQRS, черг, Redis і UI-кіта.
- **Інтерфейс з'являється разом із другою реалізацією.** Поки реалізація одна, це просто клас або функція.
- **Фіча = одна папка на бекенді й одна на мобільному** з тією самою назвою.
- **Postgres — єдине джерело стану.** Ліміти, лічильники й метрика активації рахуються з таблиць.
- **TypeScript strict з першого дня.** Тести й лінтер відкладені, тож типи — єдина автоматична перевірка.

## Стек і версії

Усі версії фіксуються точно в `package.json` і записуються в `docs/decisions/0001-stack.md`.

| Частина | Вибір | Примітка |

| Бекенд | NestJS 12.4.2 (ESM) + `@nestjs/platform-node` | NodeAdapter рекомендований з 12.3, у v13 стане типовим |
| Авторизація | Better Auth + `@better-auth/expo` | версія 1.7.20; email і пароль, без соцмереж |
| База даних | Postgres 18 + Drizzle ORM 0.45.4 і drizzle-kit 0.31.11 | локально Postgres у docker compose |
| Валідація | zod | одні схеми для API і мобільного |
| Файли | S3-сумісне сховище | локально SeaweedFS у docker compose, завантаження через presigned URL |
| AI | vision-модель зі структурованою відповіддю | провайдера обираємо після тесту точності |

## Бекенд

Бекенд має три зони: `modules/` для бізнес-фіч, `infra/` для підключень до зовнішніх систем і `common/` для наскрізних речей. Крон, вебсокети й черги — це не окремі модулі, а ще один вхід у фічу, тому вони живуть у її папці з фіксованим суфіксом.

```
modules/looks/
├─ looks.module.ts
├─ looks.controller.ts    HTTP-вхід
├─ looks.service.ts       логіка й запити Drizzle
├─ looks.schema.ts        таблиці цієї фічі
├─ looks.prompt.ts        промпт для моделі, якщо фіча її викликає
├─ looks.gateway.ts       вебсокети, коли знадобляться
├─ looks.cron.ts          задачі за розкладом, коли знадобляться
└─ looks.listener.ts      реакція на події інших модулів
```

На старті в папці фічі лише перші чотири файли; решта додається, коли з'являється потреба. Шару репозиторіїв немає: сервіс пише запити Drizzle напряму.

Схема: Expo-застосунок (Expo Router, TanStack Query) звертається до API через `/v1`. API — це NestJS на NodeAdapter з модулями `auth`, `products`, `stash`, `looks`, `repeat` і зоною `infra` (`ai`, `storage`, `db`). За API стоять vision-модель, S3-сховище і Postgres.

Застосунок звертається тільки до API. Виняток один: фото вантажиться прямо в сховище за посиланням, яке видає модуль `storage`.

| Де | За що відповідає | Етап |
| --- | --- | --- |
| `infra/db` | клієнт Drizzle, міграції | 0 |
| `modules/auth` | реєстрація, вхід, сесія, guard, профіль | 0 |
| `infra/storage` | presigned URL для фото | 1 |
| `infra/ai` | клієнт моделі: промпт, фото і схема на вході, перевірений об'єкт на виході | 1 |
| `modules/products` | каталог, пошук, штрихкод, продукти, створені користувачками | 1 |
| `modules/stash` | косметичка, розпізнавання продуктів із фото столу | 1 |
| `modules/looks` | публікація образу з продуктами, профіль, проста стрічка | 2 |
| `modules/repeat` | розбір образу, порівняння з косметичкою, близькість, інструкція | 3 |
| `modules/social` | підписки, реакції, коментарі, збережене | 4 |
| `modules/moderation` | скарги й блокування | 5 |

Межі між зонами:

- **Напрям залежностей один.** `modules` імпортують `infra` і `common`; `infra` і `common` ніколи не імпортують `modules`.
- **Модуль бачить інший модуль лише через його експортований сервіс.** До чужих таблиць і файлів напряму не звертається.
- **Новий транспорт = нова папка в `infra/`, обробники лишаються у фічах.** Наприклад, `infra/scheduler` підключає розклад, а самі задачі лежать у `repeat.cron.ts`.
- **Таблиці лежать поруч із фічею.** `drizzle.config.ts` збирає їх за шаблоном `src/modules/**/*.schema.ts`.
- **Підпапки всередині модуля з'являються, коли файлів стає більше восьми,** не раніше.

Правила:

- **Запуск.** `NestFactory.create(AppModule, new NodeAdapter())`, префікс `/v1`, один фільтр помилок із форматом `{ code, message }`.
- **Валідація.** Схема zod із `packages/contracts` проходить через один pipe. Типи виводяться зі схем, окремих DTO-класів немає.
- **Авторизація.** Екземпляр Better Auth з адаптером Drizzle і плагіном `expo()` живе в `modules/auth/auth.ts`. Глобальний guard читає сесію, відкриті маршрути позначаються `@Public()`.
- **AI.** Один `AiService` в `infra/ai` з одним методом. Промпти лежать у модулі своєї фічі, відповідь моделі перевіряється zod і зберігається як jsonb.
- **Ліміт інструкцій.** Кількість рядків `repeat` користувачки за сьогодні; Redis не потрібен.
- **Списки.** Курсорна пагінація всюди, де список може рости.

**Better Auth на NodeAdapter перевірено 11.11.2026: працює власна тонка інтеграція без сторонніх бібліотек.** Версії спайку: NestJS 12.4.2, Better Auth 1.7.20, Drizzle ORM 0.45.4, Node 24.15. У `main.ts` порядок такий: `bodyParser: false`, далі `app.use('/api/auth', toNodeHandler(auth))`, і лише потім `app.useBodyParser(...)`. Повний звіт: `docs/decisions/0002-better-auth-node-adapter.md`.

- **Обробник `/api/auth/*` стоїть поза конвеєром Nest.** Guard-и, interceptor-и й префікс `/v1` на нього не діють; логування чи rate-limit для нього підключаються через `app.use` перед монтуванням.
- **Ніщо, що читає тіло запиту, не реєструється перед обробником Better Auth.** Це фіксується коментарем у `main.ts`.
- **Guard читає сесію з Postgres на кожен захищений запит.** `session.cookieCache` вмикаємо, коли з'явиться навантаження.
- **Власні запити мобільного до `/api/auth/*`** мають нести заголовок `expo-origin`; клієнт `@better-auth/expo` додає його сам.
- **Код зі спайку** (`main.ts`, `auth.ts`, guard, декоратори) переноситься в `modules/auth`.

## Мобільний застосунок

Файли маршрутів тонкі: вони лише збирають екран із того, що лежить у `src/features/`.

```
app/
├─ _layout.tsx        провайдери: QueryClient, перевірка сесії
├─ (auth)/            sign-in, sign-up, quiz
├─ (tabs)/            index (Стрічка), stash (Косметичка), profile
├─ add.tsx            меню «+»: фото столу, сканер, образ, повторити
├─ look/[id].tsx      образ: порівняння, потім інструкція
└─ settings.tsx
```

Правила:

- **Фіча.** `src/features/<назва>/` містить `api.ts` (хуки запитів і мутацій) та компоненти цієї фічі.
- **Мережа.** Одна обгортка над `fetch` у `src/lib/api.ts`: додає cookie сесії Better Auth і перевіряє відповідь схемою з `contracts`.
- **Сесія.** `authClient` з плагіном `expoClient` і `expo-secure-store`; стан входу береться з `useSession`, окремого стору немає.
- **Вигляд.** `StyleSheet` і один `theme.ts` з токенами. Бренд ще не готовий, тож заміна кольорів і шрифтів має бути правкою одного файлу.
- **Базові компоненти.** П'ять-шість у `src/ui/`: Screen, Text, Button, Input, Card.
- **Нативні модулі.** `expo-secure-store`, `expo-network`, `expo-image`, `expo-image-picker`, `expo-image-manipulator`; `expo-camera` для штрихкодів додається на етапі 1.
- **Дозволи.** Тексти `NSCameraUsageDescription` і `NSPhotoLibraryUsageDescription` задаються в `app.json`.
- **Ідентифікатори.** Bundle ID реєструється в акаунті Apple Developer до першого TestFlight. Схема застосунку (`makeupstash`) додається в `trustedOrigins` Better Auth.

## Модель даних

Таблиці додаються разом з етапом, який їх уперше використовує; кожна має `id` і `created_at`.

| Таблиця | Ключові поля | Етап |
| --- | --- | --- |
| `user`, `session`, `account`, `verification` | генерує CLI Better Auth | 0 |
| `profile` | user_id, username, bio, avatar_key, stash_public | 0 |
| `product` | brand, name, category, source, external_id, created_by | 1 |
| `shade` | product_id, name, color_family, finish, barcode | 1 |
| `stash_item` | user_id, product_id, shade_id (необов'язковий), added_via | 1 |
| `stash_scan` | user_id, image_key, candidates (jsonb), accepted_count | 1 |
| `look` | author_id, image_key, caption | 2 |
| `look_product` | look_id, product_id, shade_id | 2 |
| `repeat` | user_id, look_id або image_key, analysis (jsonb), matches (jsonb), closeness, steps (jsonb), repeated_at, feedback | 3 |
| `follow`, `reaction`, `comment`, `saved_look` | пари ідентифікаторів і тип | 4 |
| `report`, `block` | хто, на що, причина | 5 |

- **Фото столу.** AI повертає кандидатів, сервер шукає їх у `product`; у косметичку потрапляє лише те, що користувачка підтвердила. `stash_scan` зберігає пропозиції, щоб рахувати точність розпізнавання.
- **Відтінок необов'язковий.** На фото упаковки його часто не видно, тому `stash_item` може посилатися лише на продукт.
- **Продукт поза каталогом** створюється з `source = user` і `created_by`; так каталог росте сам.
- **Порівняння з косметичкою** йде за `category` і `color_family`, тому обидва поля — enum-и Postgres.
- **Близькість** (`repeat.closeness`, 0–100) рахується з `matches`: точний збіг, заміна чи відсутність для кожного елемента образу.
- **«Повторила»** — це `repeat.repeated_at`; звідси метрика «справжній успіх».
- **Цифри етапів і активація** рахуються SQL-запитами з цих таблиць. Аналітичний SDK не потрібен.

## Документація

Один файл відповідає на одне питання і вміщується на один-два екрани; каркас усіх файлів створюється на етапі 0.

```
README.md             запуск за 5 хвилин: вимоги, команди, посилання на docs/
AGENTS.md             короткі правила для AI-асистентів і нових людей
docs/
├─ README.md          зміст: що де шукати
├─ plan.md            цей план і статус етапів
├─ concept.md         концепція продукту
├─ architecture.md    схема, модулі, шлях запиту
├─ conventions.md     назви, склад фічі, формат помилок, що заборонено
├─ data-model.md      таблиці, зв'язки, enum-и
├─ api.md             ендпоінти за модулями
├─ ai.md              промпти, схеми відповіді, ліміти, оцінка точності
├─ setup.md           локальне середовище і змінні оточення
├─ release.md         підпис, EAS, TestFlight, вимоги сторів
└─ decisions/         один короткий файл на рішення: 0001-stack.md, …
```

- **Зміна документації йде тим самим комітом, що й зміна коду.** Інакше файли застаріють за два тижні.
- **Рішення** записується в 5–10 рядків: контекст, що вирішили, наслідки. Перші три: стек, власна інтеграція Better Auth, відсутність шару репозиторіїв.
- **`conventions.md` — найважливіший файл.** Він тримає фундамент рівним, коли коду стане більше.
- **`AGENTS.md`** посилається на `conventions.md` і `architecture.md`, а не дублює їх.

## Етапи

Кожен етап перевіряє одне припущення і закінчується тим, що можна показати на телефоні.

### Етап 0. Скелет

Готово, коли з iPhone можна зареєструватися, увійти, і `GET /v1/me` повертає профіль.

- [ ] Монорепозиторій: pnpm workspaces, `.nvmrc`, спільний `tsconfig` зі strict
- [ ] API: NestJS 12 на NodeAdapter, `env.ts`, `/v1/health`
- [ ] Postgres і SeaweedFS у docker compose, Drizzle, перша міграція
- [ ] Перенести інтеграцію Better Auth зі спайку та повторити перевірки a–g
- [ ] Авторизація: email і пароль, guard, `@CurrentUser`, таблиця `profile`
- [ ] Мобільний: Expo SDK 58, Expo Router, три порожні вкладки, екрани входу й реєстрації
- [ ] `packages/contracts`, обгортка `fetch`, TanStack Query
- [ ] Development build на iPhone
- [ ] Каркас `docs/` і перші три рішення

### Етап 1. Косметичка: додати продукти без зусиль

Припущення: користувачка збере косметичку з 10+ продуктів за кілька хвилин. Готово, коли з одного фото столу більшість продуктів потрапляє в косметичку, а решту можна додати сканером або пошуком.

- [ ] Обрати джерело бази продуктів і написати скрипт імпорту
- [ ] Тест розпізнавання на 10–15 фото справжніх столів до написання коду; вибір vision-моделі
- [ ] Завантаження фото: стиснення на телефоні, presigned URL
- [ ] Фото столу: AI повертає кандидатів (бренд, назва, категорія), сервер зіставляє їх із каталогом
- [ ] Екран підтвердження: прийняти, виправити або прибрати кожен продукт, обрати відтінок
- [ ] Сканер штрихкодів
- [ ] Пошук за брендом і назвою
- [ ] Продукт, якого немає в каталозі, користувачка створює сама
- [ ] Список косметички й видалення

Вимірюємо: скільки продуктів додано з одного фото, яку частку пропозицій AI прийнято без правок, скільки часу минає до 10 продуктів.

### Етап 2. Публікація образу

Припущення: опублікувати образ із продуктами можна менш ніж за хвилину. Готово, коли фото з готовим макіяжем публікується з позначеними продуктами і його видно у профілі та простій стрічці.

- [ ] Фото з камери або галереї
- [ ] Швидкий вибір продуктів: спершу власна косметичка, потім пошук
- [ ] Продукт, обраний із пошуку, одразу додається в косметичку
- [ ] Сторінка образу зі списком продуктів
- [ ] Профіль з образами і стрічка всіх образів за часом

Вимірюємо: час від фото до публікації, скільки продуктів позначено, яка частка взята з косметички. Відео додається пізніше в той самий потік.

### Етап 3. «Повтори цей образ»

Припущення: порада з власної косметички настільки корисна, що образ справді повторюють. Готово, коли для завантаженого фото або образу зі стрічки отримуєш план повторення своїми засобами й оцінку, наскільки близько вийде.

- [ ] Тест точності AI-розбору макіяжу на 20–30 фото до написання коду
- [ ] AI-розбір фото в структуру й екран, де його можна виправити
- [ ] Для образу зі стрічки розбір не потрібен: продукти вже вказала авторка
- [ ] Порівняння з косметичкою: є, чим замінити з поясненням, не вийде
- [ ] Оцінка близькості: загальна і для кожного елемента образу
- [ ] Покрокова AI-інструкція з позначкою «згенеровано AI» і лімітом 2 на день
- [ ] «Повторила» та оцінка інструкції

Вимірюємо: яка частка дійшла до інструкції, яка натиснула «Повторила», скільки оцінок «не вийшло».

### Етап 4. Спільнота

Готово, коли стрічка складається з підписок і популярного, а на образ можна відреагувати.

- [ ] Підписки, чужий профіль і публічна косметичка
- [ ] Стрічка: популярне і підписки
- [ ] Реакції, «Зберегти», коментарі
- [ ] Пошук користувачок і образів простим запитом
- [ ] Сповіщення списком усередині застосунку
- [ ] Квіз при реєстрації, якщо фото столу не закриває перший запуск

### Етап 5. Перед публічним запуском

Готово, коли збірка проходить рев'ю App Store.

- [ ] Скарги на образи й коментарі, блокування користувачки, правила спільноти
- [ ] Видалення акаунта із застосунку
- [ ] Налаштування приватності
- [ ] SQL-запит метрики активації
- [ ] Політика приватності, віковий рейтинг 16+, статус DSA

App Store вимагає видалення акаунта в застосунках із реєстрацією, а для користувацького контенту — скарги, блокування й модерацію.

## Що не входить у MVP

- Тести й лінтер; повертаємось до них після перевірки ядра.
- Redis, черги, вебсокети, мікросервіси.
- Адмін-панель: модерація на старті йде через SQL або Drizzle Studio.
- Вхід через соцмережі. Щойно з'явиться Google чи інший сторонній вхід, App Store вимагатиме ще й Sign in with Apple.
- Push-сповіщення, аналітичний SDK, веб-версія, бібліотека перекладів (рядки лежать в одному файлі українською).
- Усе з розділів «Пізніше» і «Платна підписка» концепції.

## Ризики й відкриті рішення

| Ризик або питання | Що робимо |
| --- | --- |
| AI не впізнає продукти на фото столу або плутає їх | тест на 10–15 фото до етапу 1; AI лише пропонує, користувачка підтверджує; відтінок обирається вручну |
| Розпізнаного продукту немає в каталозі | користувачка створює продукт сама; сканер і пошук лишаються запасним шляхом |
| Немає бази продуктів і штрихкодів для України та Європи | вирішити до початку етапу 1; перевірити покриття відкритих баз на кшталт Open Beauty Facts |
| Точність AI-розбору макіяжу | тест на 20–30 фото до етапу 3; порівняння за категорією й сімейством кольору; користувачка виправляє розбір |
| Вартість AI | стиснення фото, ліміт 2 інструкції на день; ліміт на фото столу вводимо за фактичними витратами |
| Інтеграція Better Auth залежить від порядку middleware і перевірена лише на NestJS 12.4.2 | коментар у `main.ts`; повторювати перевірки a–g при оновленні NestJS чи Better Auth; запасний варіант — `platform-express` |
| NodeAdapter вийшов лише в NestJS 12.3 | фіксуємо версію, не пишемо код, прив'язаний до адаптера |

Рішення, які лишаються відкритими:

- [ ] Провайдер vision-моделі
- [ ] Джерело бази продуктів і відтінків
- [ ] Хостинг API та Postgres (підійде будь-який, що запускає один Node-процес і керований Postgres)
- [ ] Чи обов'язковий username при реєстрації
